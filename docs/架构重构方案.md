## 一、现状审阅结论

代码已全量通读（28 个 .kt，约 4000 行）。功能层面 v0.2.1 已能跑通主流程，但存在 **2 个确认的数据 bug、3 个架构缺陷、若干功能/质量问题**。

### A. 确认的数据 bug（最高优先级）

| # | 问题 | 位置 | 证据 |
|---|------|------|------|
| A1 | **高度/深度单位制与桌面版不一致**：模型按 `米×1000` 存储，但桌面版 ChangeAltitude 反汇编确认为 `实际值 = 存储值 ÷ 180.0`（divsd 180.0）；且 `applyAltitudeDepth` 中 `wp.assignedAltDepth * 1000L` 对已是存储单位的值重复乘算 | Unit.kt / MovementEngine.applyAltitudeDepth | asm `ChangeAltitude.asm` 0x1406c9893 `divsd xmm1, xmm0`（xmm0=180.0）|
| A2 | **护航队 formationDistance 单位混乱**：`createConvoy` 写入 `2000`（语义=码），`moveFormations` 按 `formationDistance × NMI_SCALE`（海里×10⁵）解释 → 编队成员会被甩到 2000 海里外 | MainActivity.createConvoy / MovementEngine.moveFormations | 读代码对照 |

### B. 架构缺陷（重构的核心动因）

| # | 问题 | 后果 |
|---|------|------|
| B1 | **MainActivity 上帝对象**（581 行）：UI、业务逻辑（doTurn/复制/护航队）、状态（12 个 mutableStateOf）、文件 IO 全混在一处，无 ViewModel | 旋转丢状态、逻辑不可测、改动牵一发动全身 |
| B2 | **状态管理靠 hack**：`turnTick++` 手动触发重组（因 ScenarioFile 就地可变、引用不变），散落在 Activity 各方法 | 漏触发 = 界面不刷新；触发 = 全画布重组，性能差 |
| B3 | **渲染层不纯**：MapRenderer 把 JSON 解析（产生 android.graphics.Path）与绘制混在一起；Camera 直接依赖 compose-runtime | 引擎/渲染逻辑无法纯 JVM 单测，只能靠 Gradle 全量构建验证 |

### C. 功能缺陷

| # | 问题 |
|---|------|
| C1 | **测量手势冲突**：测量模式的 drag 与地图平移的 transform-pan 在两个并行 pointerInput 块中同时生效，测量时单指拖动会同时平移地图 |
| C2 | **回放性能 O(n·m·parse)**：`positionAt` 每帧对每单位每轨迹点做 `TimeUtil.parse` 字符串解析，大场景掉帧 |
| C3 | **Range 耗尽"继续移动"语义错误**：桌面版 Continue = 无视 Range 继续航行；我们实现成"下一回合仍 0 距离不动" |
| C4 | **运动命令导出格式自创**：`{Units:[...]}` 为自造结构，未对照桌面版 `MovementOrders.BuildUnitArray` 的真实格式 |
| C5 | 弧默认值/ActiveSensors 标记已小修（未提交），ActiveSensors 样式因 asm 缺失属推断实现，需真机对照 |

### D. 代码质量（随重构顺手解决）

- `kotlin.Unit` 与模型 `Unit` 冲突 → 全限定名满天飞（应 `import ...Unit as SimUnit`）
- MainActivity 中 `f2@ file?.let` 标签滥用
- 每帧 `new Paint`，无对象复用

## 二、目标架构

**MVVM + 单向数据流**，分层职责单一，引擎/数据/解析纯 Kotlin 可测：

```
┌──────────────────────────────────────────────┐
│ UI 层（Compose）                               │
│  MainScreen / SceneCanvas / Dialogs            │
│  只渲染状态 + 上抛事件，零业务逻辑                 │
├──────────────────────────────────────────────┤
│ ViewModel 层                                   │
│  GameViewModel                                 │
│  - 持有 ScenarioFile + revision 显式版本号       │
│  - StateFlow<GameUiState> 驱动 UI              │
│  - 所有操作（doTurn/undo/edit/复制…）集中于此     │
├──────────────────────────────────────────────┤
│ 引擎层（纯 Kotlin，无 Android 依赖，可单测）        │
│  MovementEngine / TurnState / FogOfWar         │
│  ReplayEngine / FormationEngine(新)             │
├──────────────────────────────────────────────┤
│ 数据层（纯 Kotlin）                              │
│  model（数据类）/ codec（Gson+SpScn）            │
│  repo（SAF 文件 IO，唯一碰 Android 的薄壳）        │
├──────────────────────────────────────────────┤
│ 渲染层                                         │
│  MapDataParser（纯 Kotlin：JSON→数据类）         │
│  Camera（纯数学：坐标变换，不依赖 compose）        │
│  Painter 组（android.graphics 薄壳，只画不算）    │
└──────────────────────────────────────────────┘
```

**核心决策**：

1. **显式 revision 替代 turnTick**：ViewModel 内 `var revision` 每次操作后自增，`GameUiState` 携带 revision 作为重组 key。语义与 turnTick 相同，但收敛到一处、可追踪。
2. **ScenarioFile 保持就地可变**（与 Gson/引擎现状兼容），不伪装修饰不可变；可变性被 ViewModel 收口，UI 不直接碰。
3. **渲染层拆两半**：解析（纯 Kotlin，产出数据类/点列表）与绘制（android.graphics）分离 → 解析逻辑可纯 JVM 单测（BoundaryRect/多边形/标注坐标 ×10 换算都能测）。
4. **Camera 去 compose 依赖**：纯数学 API（zoom/pan/fitBounds 操作普通数值），Compose 状态包装放 UI 层。

## 三、编程计划（分阶段，每阶段独立可验收、独立发版）

### Phase 0 — 确定性 bug 止血（不动架构）
- 修 A1：高度/深度单位制对齐桌面版（÷180 语义，全面核对模型 Altitude/Depth/Assigned*/Climb/Descend/Ascend/DescRate 全链路）
- 修 A2：护航队 formationDistance 单位统一（码→文件单位换算走 CoordUtil.yardsToFile）
- 修 C1：测量手势与地图平移互斥（手势路由）
- 修 C3：Range 耗尽"继续移动"= 无视 Range 继续（对齐桌面版）
- 顺手：import alias 清理、提交当前 3 个未提交小改动
- **验收**：新增 JUnit（高度/深度换算、编队距离、Range 继续语义）；现有 35 测试全过；构建 APK

### Phase 1 — 架构重构（最大改动，一次到位）
- 新建 `GameViewModel`：状态集中 + revision + 所有业务操作入口
- `MainActivity` 瘦身至 <200 行：只做 Compose 组合 + 事件转发
- 渲染层拆分：`MapDataParser`（纯 Kotlin）/ `MapPainter` / 纯数学 `Camera`
- **验收**：功能回归清单（打开/保存/Do/Undo/Next/回放/测量/编辑/复制/护航队/导出全手动过一遍）；测试全过；构建 APK

### Phase 2 — 引擎补全（对齐桌面版）
- 高度/深度引擎完整实现（Climb/Descend 速率、单回合 180 上限，按反编译逐条核对）
- 编队移动三模式（Compass / RelativeToCourse / Column）
- 运动命令导出格式对齐 `MovementOrders.BuildUnitArray`
- **验收**：对照反编译伪代码逐条核对；极地行动回归基准；测试

### Phase 3 — 渲染/交互增强
- 符号系统可选样式（CWS / WW2 / NTDS）
- 空间索引（单位数量大时的命中检测/裁剪优化）
- 回放性能优化（预排序 + 双指针）+ 测量 CSV 导出
- **验收**：真机对照桌面版

### Phase 4 — 验证与发布
- 全量 JUnit + 真实存档（Iron Bottom Sound）字节级回归
- APK 真机测试
- 每阶段均走 `scripts/release.sh` 流程发版

## 四、执行约束

- 每阶段结束才发版，版本号递增（0.2.2 / 0.3.0 / …）
- 所有引擎/解析层改动必须先有 JUnit 再实现
- 算法存疑时以桌面版反编译 asm 为准，不猜测
- 每阶段完成写当日 memory
